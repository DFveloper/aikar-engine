# CPU 모델 추론 및 학습 최적화

이 저장소의 CPU 백엔드에서 모델 추론과 학습의 병목을 찾아 최적화하라. 실제 모델 실행 시간과 메모리 사용량을 개선하되, 계산 정확성, 모델 품질, 학습 의미를 유지해야 한다. 단순한 설정 변경에 그치지 말고 측정으로 확인한 병목에 대해 작고 검토 가능한 코드 개선을 수행하라.

## 작업 범위

- 추론: prompt processing(prefill), token generation(decode), dense/MoE 행렬 연산, 양자화 및 역양자화, attention과 KV cache, 스레드 분배와 메모리 접근을 조사한다.
- 학습: 저장소가 CPU에서 지원하는 fine-tuning, QLoRA, QLion/QAT 경로 중 실행 가능한 경로의 forward, backward, gradient accumulation, optimizer update, 데이터 준비 비용을 조사한다. 지원되지 않는 학습 모드를 새로 구현하는 것은 이 태스크의 범위가 아니다.
- `ggml/src/ggml-cpu/`, `ggml/src/ggml-opt.cpp`, `src/`, `examples/training/`, `examples/qlora_training/`의 기존 구현을 우선 활용한다.
- 추론과 학습 모두 로컬에 사용 가능한 Pulsar S 모델을 최우선으로 사용한다. Pulsar S를 사용할 수 없거나 해당 실행 경로에서 지원하지 않으면 사유를 기록하고 다른 Lumen/Pulsar 계열 모델을 사용한다. 모델 이름이나 과거 문서만으로 현재 파일 경로, 하드웨어, 지원 기능을 가정하지 않는다.

## 진행 방법

1. 저장소 지침과 `skills/code-review/SKILL.md`를 읽는다. 기존 변경 사항을 확인하고 보존한다. 관련 과거 보고서는 참고하되 현재 소스와 실행 결과로 다시 확인한다.
2. CPU 모델, 코어/스레드 수, SIMD 지원, RAM, NUMA 구성, 컴파일러와 빌드 옵션을 확인한다. 모델 및 데이터 경로와 식별 정보, 양자화 형식, 실행 옵션을 기록한다.
3. CPU 전용 실행으로 변경 전 기준선을 확보한다. GPU offload를 끄고 실제 사용 백엔드를 확인한다. 기존 작업물을 포함한 현재 상태를 기준으로 별도의 빌드 및 결과 디렉터리를 사용한다.
4. 추론은 짧은/긴 prompt와 단일/다중 token 작업을, 학습은 고정 데이터로 여러 optimizer step을 측정한다. 하드웨어와 자원에 맞는 대표 사례를 선택하고 테스트 행렬을 기록한다.
5. 프로파일링으로 연산 시간, 메모리 대역폭, activation 변환 및 재패킹, thread synchronization, 임시 버퍼 할당 비용을 구분한다. 추론과 학습 각각에서 가장 큰 병목을 우선 검토한다.
6. 기존 SIMD, repack, GEMM/GEMV, 스레드풀 및 workspace 경로를 재사용해 유효한 개선을 구현한다. 한 번에 하나의 가설을 검증하고, 효과가 없거나 회귀하는 실험은 최종 변경에서 제외한다.
7. 동일한 조건으로 변경 전후를 비교하고, 실제 채택한 변경과 제외한 실험의 근거를 보고한다.

## 검증 기준

- `llama-bench`로 prefill과 decode의 tok/s를 따로 측정하고 peak RSS를 기록한다. 서버 경로를 바꿨다면 같은 요청으로 TTFT와 전체 요청 시간도 확인한다.
- 학습은 고정 seed, 데이터 순서, context, batch/microbatch, supervised token 수, optimizer 설정에서 step 시간, 학습 tok/s, peak RSS를 측정한다. 초기화 및 데이터 로딩 시간은 정상 상태의 step 시간과 구분한다.
- 워밍업 후 각 성능 사례를 최소 3회 측정하고 중앙값과 변동 범위를 보고한다. 성능 측정은 순차 실행해 자원 경쟁을 피한다. 모델, thread 수, affinity, 빌드 옵션을 바꾼 실험은 코드 개선 효과와 구분한다.
- 변경 영역에 맞춰 `test-backend-ops`, `test-quantize-fns`, `test-tiled-mulmat`, `test-opt`, `test-qat` 등 기존 테스트 중 필요한 것을 실행한다. 실행 옵션과 등록 여부는 현재 빌드에서 확인한다.
- SIMD 변경은 signed byte 극값, tail, 비정렬/strided 입력, 여러 thread 수를 확인한다. 지원 ISA를 명시하고 범용 fallback을 유지한다.
- 추론은 동일 입력의 연산 출력과 logits를 기존 허용 오차로 비교하고, 가능한 경우 고정 검증 데이터의 perplexity도 비교한다. 생성 문장이 그럴듯하다는 사실만으로 정확성을 판정하지 않는다.
- 학습은 동일 초기 상태의 loss, gradient, parameter update를 비교한다. checkpoint 저장/재개 경로에 영향을 주면 재개 후 update와 결과물 로딩도 확인한다. 짧은 smoke test로 장기 수렴을 입증했다고 주장하지 않는다.
- 성공은 대표 end-to-end 작업에서 측정 변동을 넘는 개선이 있고, 검증 범위에서 유의미한 정확성 또는 성능 회귀가 없는 경우다. 메모리와 속도의 trade-off는 수치로 명시하며 임의의 배속 목표를 달성하려고 작업량을 줄이지 않는다.

## 제약 및 결과물

- 모델 구조, 파일 형식, 공개 API, 학습 objective와 optimizer 의미를 임의로 바꾸지 않는다. 낮은 정밀도, 토큰 생략, context 축소, batch 변경을 동일 작업의 코드 가속으로 취급하지 않는다.
- 기존 사용자 변경을 되돌리거나 덮어쓰지 않는다. 모델, 데이터, checkpoint 원본을 보존하고 검증 출력은 별도 경로에 저장한다.
- 큰 구조 변경이나 새 실행 패턴이 필요하면 근거와 설계를 먼저 정리해 사용자 확인을 받는다. commit, push, PR 생성, 운영 서비스 재시작은 수행하지 않는다.
- 하드웨어, 모델 또는 데이터가 없으면 가능한 빌드/연산 검증을 수행하고, 막힌 검증과 재현 명령을 명시한다. 측정하지 않은 성능을 추정값으로 채우지 않는다.
- 최종 결과에는 변경 파일과 병목 원인, 재현 가능한 빌드/실행 명령, 변경 전후 성능 및 메모리 표, 정확성 검증 결과, 원시 로그 위치, 남은 제한을 포함한다. 추론과 학습 결과를 각각 보고하고 미검증 항목을 분명히 표시한다.
