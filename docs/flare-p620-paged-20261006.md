# Flare on P620: measured serving configuration

Flare serves four concurrent requests on the P620 with persistent System Cache, RAM conversation cache and Paged KV. Four separately warmed 8192-token histories generate 512 tokens each at 9.67-9.69 tok/s per request, meeting the requested concurrent 8-10 tok/s range. The uncached single-request baseline is 19.43 tok/s.

```sh
./scripts/serve-flare-p620-paged.sh
```

The launcher enables four slots, a 32768 MiB RAM cache and preloads both thinking variants of the fixed system prompt. For background serving, run `/mnt/openwebui/AIKAR/Lumen-3.2-Flare/start.sh`; it creates the `flare-p620` tmux session. The OpenAI-compatible API is `http://127.0.0.1:11437/v1`, model `Lumen-3.2-Flare`. Set `FLARE_HOST`, `FLARE_PORT`, `FLARE_GPU`, `FLARE_MODEL_DIR`, `FLARE_SERVER_BIN`, `FLARE_PARALLEL`, `FLARE_KV_BLOCKS`, or `FLARE_CACHE_RAM_MIB` to override their defaults. Stop the foreground server with Ctrl-C. GPU index 1 is the P620 on this host. The existing V100 server on port 11435 is independent.

## Measurements

| Configuration | Active requests | Generated tokens per request | Slowest request, tok/s | First token, seconds |
| --- | ---: | ---: | ---: | ---: |
| Historical uncached F16 baseline, GPU layers 99, threads 4 | 1 | 512 | 19.43 | 41.57 |
| Four independent RAM-restored histories, final F16 pool | 4 | 512 | 9.67 | 0.46-0.61 |
| System/RAM warm, F16 paged KV | 2 | 512 | 16.69 | 0.21-1.01 |
| System/RAM warm, F16 paged KV | 4 | 512 | 9.68 | up to 3.24 |
| System/RAM warm, F16 paged KV | 8 | 512 | 5.57 | up to 6.64 |

All rows have 8192 total input tokens per request and 512 output tokens. The independent histories differ near token 2000, are separately warmed and restore 8191 cached tokens after erasing all slots. All four slots generate concurrently at 9.667/9.676/9.686/9.694 tok/s; aggregate decode throughput is 38.67 tok/s over a common first-to-last interval. The other warm rows share a long history and differ near the end, restoring 8128-8191 cached tokens. Their aggregate decode rates are 33.29 tok/s for two slots, 38.51 for four and 44.17 for eight. Streaming rates exclude initial prompt processing and queue wait. Earlier common-history measurements used the smaller SWA pool; the independent row uses the final pool.

Four slots meet the requested concurrent 8-10 tok/s range in the common-history measurement; eight slots do not. The 16-slot Q8 experiment was interrupted and is not a completed capacity result. Prompt processing for an uncached single request is about 197 input tokens/s; a new 8K request can take about 42 seconds before its first token. Fixed System Cache reuses about 1800 tokens and can reduce this initial work. A burst of new histories or mixed prefill/generation can still reduce speed. Cache-hit measurements are not an unconditional latency or throughput guarantee. No mathematical upper-bound capacity claim is made.

Four-slot GPU allocation is about 1665 MiB, including model, context, computation and runtime overhead, leaving about 327 MiB free in the driver's available budget. The model's calculation/output layers occupy 1286.91 MiB on the GPU; large embedding tensors remain CPU mapped. The four-slot Paged F16 KV pool occupies about 244 MiB. Physical full-attention budget is 2304 pages, with 16 tokens per page. Context is 9216 tokens per slot, 36864 total, allowing four independent 8192+512 workloads without shifting.

## Implementation and verification

The Paged KV source lives in the existing isolated worktree `/tmp/aikar-paged-kv`. The primary checkout has other ongoing changes and was not replaced. The deployed binary and libraries are copied into `build-flare-p620/bin`; the full source snapshot is `build-flare-p620/sources.tar.gz`. `build-flare-p620/shared-kv.patch` contains only this task's changes relative to the saved worktree inputs.

Flare stores KV in its first 15 layers. The remaining 20 layers reuse the matching source layer, index 13 for sliding attention and index 14 for full attention, including its physical pages and graph K/V inputs. Shared-layer geometry is checked before reuse. State serialization uses stable encounter-order page identifiers so a restore into different physical pages produces the same state blob.

The SWA pool includes ubatch and page-boundary headroom for every slot. Four independent saved histories can each retain 48 pages; the original 152-page pool rejected the fourth restore. The revised four-slot pool has 200 pages and occupies 253.50 MiB together with the full-attention cache. The before-fix failure log is retained beside the independent-history measurement.

The serving default is reasoning off. The template adds the same closed thought-channel marker used by Pulsar when thinking is disabled. Both thinking variants of the system prefix remain preloaded. The measured 8K throughput rows precede this final generation-prefix adjustment; attention workload and cache budgets are unchanged. Live chat checks verify Korean text, a greeting within a 256-token response, and 1808 system-prefix cache hits. The model still emits planning prose in content despite reasoning off; concise answer quality is not guaranteed by this serving change.

To rebuild the source snapshot in an empty directory:

```sh
tar -xzf /home/user/aikar-engine/build-flare-p620/sources.tar.gz
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=61 -DLLAMA_BUILD_UI=OFF
cmake --build build -j 4 --target llama-server
```

Existing CUDA Paged Attention checks passed all 34 selected cases, including F16/Q8, 8192-token positions, irregular masks and cache writes. Existing fragmented-state and save/load tests passed for F16 and Q8. The fragmented-state tests used 767 tokens per sequence across three sequences, exceeding the 512-token sliding window. Fragmented versus clean paged logits had maximum absolute error 0. State copy, asynchronous copy, malformed-state rejection, byte-identical state round trip and continuation checks passed. Device-only state tests are skipped by the existing paged implementation.

Paged versus ordinary KV is not bit-identical. In the long F16 comparison, maximum absolute logit differences were 1.57 before restore and 2.20 after continuation, with relative squared errors about 0.007 and 0.006; compared greedy tokens matched. Intermediate callback traces show small attention differences before shared layers which can grow after quantized projections. This is evidence of numerical differences, not a proof of output equivalence or a model-quality evaluation. Both ordinary and paged continuation were inspected; strict numerical parity is not claimed.

Pascal subwarp/tiled dispatch, forced CUDA graphs and fused decode experiments did not improve the selected workload and were removed. The retained change does not alter CPU/CUDA attention kernels. The server additionally ports Pulsar's fixed system-prefix preload/restore and RAM restore fallback for paged sliding-window caches. RAM entry selection prioritizes the longest reusable token prefix, with retention fraction as a tie-breaker: previously a short 1824-token entry could prevent selection of an 8128-token prefix. The successful concurrent cache-hit sweep verifies that regression. The Flare Base chat template is retained with the Pulsar static instructions inserted and only the model identity changed to Flare.

## Reproduce the throughput measurement

```sh
FLARE_BENCH_INDEPENDENT=1 python3 scripts/bench-flare-p620-cache.py 4
python3 scripts/bench-flare-p620-cache.py 2 4 8
python3 scripts/bench-flare-p620.py '[{"tag":"repeat-np1-f16-512","users":1,"ngl":99,"threads":4,"batch":9216,"ubatch":256,"extra":["-ctk","f16","-ctv","f16"]}]'
```

The cache benchmark uses its own temporary server on port 18137, checks both system-prefix variants after slot erasure, warms the conversation cache, erases slots, then verifies restoration and concurrent generation. Independent mode changes each history near token 2000, warms each separately and restores all four before measurement. It forces 512 output tokens to avoid early-EOS bias and checks actual input/output token counts. Synthetic repeated document text measures serving speed rather than answer quality. Stop the deployed server first to avoid two processes competing for the P620. JSON reports and validation logs are retained under `build-flare-p620/results`.
